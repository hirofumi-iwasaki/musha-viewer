# C2PA native verifier

The app embeds c2pa-rs 0.91.7 (MIT OR Apache-2.0), pinned together with its transitive dependencies in `native/c2pa/Cargo.lock`. A Rust toolchain of at least 1.96, Cargo, a C toolchain and the platform SDK are required. The Rust targets `aarch64-apple-darwin` and/or `x86_64-apple-darwin` must be installed for the Xcode architectures being built. Set `CARGO` to the Cargo executable if it is not on PATH. Builds use `--locked`; dependency downloads require access to crates.io. No credentials or prebuilt native binaries belong in the repository.

Linux Flutter builds invoke `scripts/build-c2pa.sh` from CMake and place `libmusha_c2pa.so` in the application's `lib` directory. macOS Xcode builds invoke the same script for each `ARCHS` architecture, combine them with `lipo`, copy the dylib into `Contents/Frameworks`, and sign it using the active build identity when signing is enabled. Xcode and an SDK supporting the configured macOS 27 deployment target are required; a Linux build cannot validate that packaging or signature.

Run `cargo test --locked --manifest-path native/c2pa/Cargo.toml` to check the native adapter and `flutter build linux` to build the application bundle. The native script can also be invoked independently. The C ABI in `native/c2pa/include/musha_c2pa.h` takes bytes and a MIME type and returns owned UTF-8 JSON; release it once with `musha_c2pa_free`. Call it on a background isolate. The caller must supply valid pointers throughout the call; the API copies neither input nor output across an FFI boundary automatically.

The SDK performs verification while reading. Default HTTP and remote-fetch features are disabled at compile time, and the per-reader context explicitly disables remote manifest and OCSP fetch. A blocking resolver explicitly rejects every HTTP request, including DID resolution, even if SDK features are unified with other dependencies later. No trust list is configured; `trust` is always `unknown`, even if the SDK reports a cryptographically valid signature. The SDK's full manifest and validation result codes are retained. The summary reports a positive signature or hard binding only when the corresponding SDK success code exists; missing evidence remains unknown. Ingredient validation is in the raw SDK report. A remote-only manifest is reported separately and is not fetched. A successful signature says nothing about whether the depicted event is true. This version accepts an in-memory buffer and has no in-flight cancellation; the caller must apply its own size limits.

The direct SDK is dual-licensed under MIT OR Apache-2.0. The native library also statically incorporates Cargo dependencies under their respective licenses; distribution requires an inventory and inclusion of the applicable license texts and notices for the exact locked dependency graph. Review `cargo metadata --locked` and the relevant package license files before shipping; the SDK's dual license does not automatically relicense its dependencies.

The signed test fixture `signed.jpg` was generated locally from the project's unsigned EXIF sample with c2pa-rs Builder and a disposable test-only P-256 certificate. The private key was discarded. Its test certificate is valid from 2026-11-01 to 2126-10-08 UTC, so the positive test depends on the system clock being within that range. Its SDK state is Valid with trust unknown. The test changes one byte near the end in memory and verifies the SDK reports `assertion.dataHash.mismatch`; `tampered.jpg` contains the same change for integration tests. `cawg-offline.jpg` is `ims_multiple_manifests.jpg` from the c2pa-rs 0.91.7 source distribution, under that project's MIT OR Apache-2.0 license. It has an identity reference that is unavailable offline, so the SDK reports an invalid overall state; tests preserve that diagnostic.

For distribution, use the appropriate Developer ID signing identity and notarization workflow; the build signs the nested dylib with `--timestamp=none` and does not itself perform notarization. Verify the final signed bundle on macOS.
